01 · MODEL

先用你已经熟悉的数据库概念来映射

Cedar 和 Lean 都不是“AI 魔法”。它们只是把你熟悉的控制点做得更显式、更可审计、更可机器检查。

你已经懂的权限系统

角色、对象、动作、条件。Cedar 把这套模型从数据库内部抽出来，变成通用 policy engine。

像独立的 execution firewall

Agent 生成 SQL 后，不直接下发。先问 Cedar：这个 principal 对这个 resource 的这个 action 是否允许？

像“对规则本身做编译期证明”

Lean 不跑 1000 个样本，而是证明一个命题对定义域中的所有 case 都成立，然后 kernel 检查证明是否合法。

真正的风险在“翻译层”

Cedar 只会判断你告诉它的 Action。若 SQL 被错误分类成 Select，policy engine 也会基于错误输入做正确判断。

03 · CEDAR

Cedar：把数据库权限问题抽象成 3 个字段

DB 专家可以把 Cedar request 看成一个通用版本的“session role + SQL operation + object”。

DB 概念 ↔ Cedar 概念

数据库世界Cedar本 PR
role / session userprincipalAnalyst::"demo-analyst"
statement / privilegeactionSelect / Delete / Other
database / table / objectresourceDatabase::"mock_analytics"
session attributescontext当前为空，可扩展环境/时间/来源

PR #20 里的 Cedar policy

permit (
  principal,
  action == CedarDemo::Action::"Select",
  resource == CedarDemo::Database::"mock_analytics"
);

forbid (
  principal,
  action == CedarDemo::Action::"Delete",
  resource == CedarDemo::Database::"mock_analytics"
);

结果：Select 明确允许；Delete 明确禁止；没有 permit 命中的其他动作走默认 DENY。

SELECT

ALLOW

读取型 SQL 通过 Cedar gate，然后 mock DB 返回结果。

DELETE

DENY

即使 Agent 生成 DELETE，执行路径在数据库前停止。

OTHER

默认 DENY

INSERT / UPDATE / DDL 等当前都不获得 permit，因此不会执行。

为什么这比 system prompt 强？
“不要删数据”写在 prompt 里，是模型行为建议；Cedar 是独立、确定性的执行控制点。模型可以犯错，但它不能自己把 Cedar 的 DENY 改成 ALLOW。
04 · LEAN

Lean：不是更高级的单元测试，而是证明“所有 case”

对于这个 PR，Lean 的工作非常小：证明一个 read-only rule 的逻辑不可能“允许 DELETE”。

“∀ action”是 formal proof 的核心：不是多跑一些 case，而是把命题本身交给证明系统检查。

PR 中的 Lean 代码

inductive SqlAction where
  | select
  | delete
  | other
  deriving DecidableEq

def cedarAllows : SqlAction → Bool
  | .select => true
  | .delete => false
  | .other => false

theorem read_only_policy_sound
    (action : SqlAction)
    (h : cedarAllows action = true) :
    action = .select := by
  cases action <;> simp [cedarAllows] at h ⊢
给 DB 专家的翻译：
定义一个只有 Select/Delete/Other 的有限枚举，再定义一张“允许矩阵”。Lean 证明：任何被矩阵标为 true 的 action，只可能是 Select。

06 · TRUST

      
最重要的一页：到底哪些东西真的被证明/保护了？
Formal verification 的常见误区是“看到 proof 就认为整个系统都正确”。实际上，保证只覆盖明确建模的那一段。

    


    

      
      
你应该把“proof”理解成局部、精确的 contract，而不是一个覆盖整条 AI→SQL→DB 链路的万能认证。

    


    

      
可以信：Cedar runtime 是独立执行 gate只要 Action 被正确构造，ALLOW/DENY 不依赖 LLM 自觉。

      
可以信：Lean theorem 对其小模型成立在 Select/Delete/Other 这个模型中，不存在 allowed=true 且 action≠select 的 case。

      
不能信：NL→SQL 已被 formal proof 覆盖自然语言理解仍是 AI 推断；用户意图可能被错误翻译。

      
不能信：当前 SQL classifier 足够健壮它只看开头 token。复杂 CTE、注释、dialect edge cases 都值得升级成 AST parser。

    


    

      DB 专家应该立刻注意的例子：
      
WITH deleted AS (
  DELETE FROM customers
  WHERE inactive = true
  RETURNING *
)
SELECT * FROM deleted;

      如果 classifier 只看到开头 WITH 就把它当作 Select，那么 Cedar 会收到错误的 Action。
      Cedar 本身会“正确处理错误输入”。所以生产版应使用真正 SQL parser / AST classification，并让 Unknown 默认 DENY。
    

  


  

    

      
07 · NEXT

      
如果把这个 Demo 升级成生产级 Data Agent
最合理的演进不是“给 Lean 写更多炫技 theorem”，而是先把 trust boundary 一层层收紧。

    

    

      
1
SQL AST classifier用真实 parser 识别 SELECT / mutation / DDL / data-modifying CTE；Unknown 默认 DENY。

      
2
Cedar resource granularity从 database 级别细化到 schema/table/column；不同 analyst / agent / environment 使用不同 principal 与 context。

      
3
DB native read-only roleCedar 是第一道 gate，数据库自己的 read-only role / RLS / transaction mode 是第二道防线。

      
4
Proof relation进一步证明 AST classifier → Cedar Action 的映射性质，而不只是证明一个手写 mirror。

      
5
Independent verification每次 PR clean build、Cedar self-test、proof build、真实数据库 sandbox 测试都由独立 verifier 重跑。
